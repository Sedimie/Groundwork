## Why Password Hashing Matters

Passwords are among the most sensitive pieces of information handled by an application. Whenever a user creates an account, the application needs a way to verify their password during future login attempts.

Storing passwords directly in a database creates a serious security risk. If an attacker gains access to the database, plaintext passwords are immediately exposed. Users often reuse passwords across multiple services, so a breach can affect accounts beyond the compromised application.

Password hashing addresses this problem by ensuring that the original password does not need to be stored.

Instead of keeping the password itself, an application stores a derived value called a **password hash**. During login, the submitted password is processed using the same hashing scheme and its result is verified against the stored value.

The objective is not to make password recovery possible. It is to make password verification possible without retaining the original password.

## Understanding Hashing

Hashing is a one-way transformation that converts input data into a fixed-length output.

A cryptographic hash function has several important properties:

- **Deterministic:** The same input produces the same output when the same parameters are used.
- **One-way:** Recovering the original input from its hash should be computationally infeasible.
- **Avalanche effect:** A small change in input produces a significantly different output.
- **Fixed-length output:** The output has a defined length regardless of the input size.

For example, two passwords that differ by only one character should produce very different hash values.

However, not every hashing algorithm is suitable for password storage. Passwords are often short, predictable, and vulnerable to guessing. A general-purpose hash function is designed to process data quickly, which also allows attackers to test enormous numbers of password guesses.

Password storage therefore requires specialized hashing algorithms designed to make each guess expensive.

## Hashing vs. Encryption

Hashing and encryption are different approaches to protecting information.

| Property | Hashing | Encryption |
| --- | --- | --- |
| Direction | One-way | Reversible |
| Original data recovery | Not intended to be possible | Possible with the correct key |
| Main purpose | Integrity and verification | Confidentiality |
| Password storage | Appropriate | Generally inappropriate |

Encryption is useful when an application must retrieve the original information later. Password verification does not require recovering the original password, so password hashing is the appropriate approach.

## Why Ordinary Hash Functions Are Not Enough

Algorithms such as SHA-256 and SHA-512 are widely used in cryptography, but their speed makes them unsuitable as standalone password-storage mechanisms.

An attacker who obtains a database of password hashes can perform an offline guessing attack:

1. Obtain the stored password hashes.
2. Guess a possible password.
3. Calculate its hash.
4. Compare the calculated result with the stolen hash.
5. Repeat until a match is found.

Modern hardware, GPUs, and specialized cracking systems can perform huge numbers of fast hash calculations.

Password hashing algorithms solve this problem by introducing configurable computational and memory costs. Each password guess becomes more expensive, reducing the number of guesses an attacker can perform.

## Understanding Salt

A **salt** is a randomly generated value added to a password as part of the hashing process.

Every password should receive its own unique salt, even when two users choose the same password.

Consider two users who both select the password `example123`.

Without unique salts, both passwords may produce identical stored hashes. With unique salts, their resulting password hashes will differ.

Salting provides several important protections:

- Prevents identical passwords from automatically producing identical stored hashes.
- Makes precomputed rainbow-table attacks impractical.
- Forces attackers to perform separate calculations for each salted password.

A salt is not a secret. It is stored alongside the password hash and is required for verification.

For password hashing, a randomly generated salt of at least 16 bytes is a common recommendation.

## Understanding Pepper

A **pepper** is an additional secret value used alongside password hashing.

Unlike a salt, a pepper is shared across a system or application and must be stored separately from the password database, such as in a secure secrets manager.

If an attacker steals only the database, the pepper provides an additional barrier because the database alone does not contain all the information needed to reproduce password verifiers.

Salt and pepper serve different purposes:

| Salt | Pepper |
| --- | --- |
| Unique for each password | Usually shared across an application |
| Public | Secret |
| Stored with the password hash | Stored separately |
| Protects against precomputed attacks | Adds protection if only the database is compromised |

A pepper is an additional defense, not a replacement for a strong password hashing algorithm.

## What Makes a Password Hashing Algorithm Secure?

A suitable password hashing algorithm should have the following characteristics:

- **Adaptive cost:** Its computational expense can be increased as hardware becomes faster.
- **Memory hardness:** It requires significant memory resources, making large-scale parallel attacks more expensive.
- **Unique salts:** It supports a different salt for every password.
- **Reliable verification:** It allows an application to verify a submitted password without storing the original password.

These properties make specialized password hashing algorithms more suitable than ordinary cryptographic hash functions.

## Modern Password Hashing Algorithms

Several algorithms have been designed specifically for password storage.

### Argon2

Argon2 was selected as the winner of the Password Hashing Competition in 2015.

It is a memory-hard password hashing function designed to make large-scale password guessing more expensive.

Argon2 has three variants:

- **Argon2d:** Uses data-dependent memory access. It is designed for environments where side-channel attacks are not a concern.
- **Argon2i:** Uses data-independent memory access and is designed to reduce certain side-channel risks.
- **Argon2id:** Combines the approaches of Argon2i and Argon2d, balancing resistance to side-channel attacks and brute-force attacks.

For general-purpose password storage, **Argon2id is the recommended variant**.

### bcrypt

bcrypt is an adaptive password hashing algorithm based on the Blowfish cipher.

Its main configurable parameter is the work factor, which determines how expensive password verification becomes.

It has been widely used in web applications and remains relevant for existing systems. However, it has a 72-byte password input limitation that developers must account for.

### scrypt

scrypt is a memory-hard password-based key derivation function.

It was designed to make large-scale attacks expensive by requiring substantial memory resources in addition to computational work.

Its parameters control the CPU and memory costs of the hashing operation.

### PBKDF2

PBKDF2 stands for Password-Based Key Derivation Function 2.

It repeatedly applies a pseudorandom function to a password and salt. Its computational cost is controlled through an iteration count.

PBKDF2 is commonly used in environments requiring approved or FIPS-compatible cryptographic implementations.

It remains a suitable option when required by a compliance environment, provided it is configured according to current recommendations.

## Comparing Password Hashing Algorithms

| Algorithm | Main strength | Important consideration |
| --- | --- | --- |
| Argon2id | Memory hardness and balanced side-channel protection | Preferred modern choice |
| bcrypt | Adaptive computational cost | 72-byte input limitation |
| scrypt | Memory-intensive computation | Requires careful resource configuration |
| PBKDF2 | Broad compatibility and approved implementations | Relies primarily on repeated computation |

The appropriate algorithm depends on the application's security requirements, available resources, and compliance constraints.

## Understanding Argon2id Parameters

Argon2id is not defined by its algorithm name alone. Its security and performance depend on configurable parameters.

Three parameters are particularly important.

### 1. Memory Cost (m)

Memory cost determines how much memory is required for one password-hashing operation.

It is generally expressed in kibibytes (KiB).

Increasing memory cost makes password guessing more resource-intensive, particularly for attackers attempting to process many guesses in parallel.

### 2. Time Cost (t)

Time cost determines the number of passes performed over the allocated memory.

Increasing the number of passes increases the computational work required for each password verification.

A higher time cost makes individual guesses more expensive but also increases the time required for legitimate authentication.

### 3. Parallelism (p)

Parallelism determines the number of independent computational lanes used by Argon2.

It allows the algorithm to use multiple processing resources during computation.

Parallelism does not simply multiply the total memory requirement or act as another iteration count. It influences how the computation is organized.

### How the Parameters Work Together

| Parameter | Controls | Increasing it generally means |
| --- | --- | --- |
| Memory (m) | Memory allocation | Greater memory requirement |
| Time (t) | Number of passes | More computation |
| Parallelism (p) | Computational lanes | More parallel processing |

These parameters must be considered together. Increasing one parameter does not automatically provide the same security benefit as increasing another.

## Choosing Appropriate Argon2id Parameters

There is no single configuration that is optimal for every application.

The OWASP Password Storage Cheat Sheet recommends a minimum Argon2id configuration of:

- Memory: 19 MiB
- Iterations: 2
- Parallelism: 1

RFC 9106 also defines two recommended configurations:

- **First recommended option:** Argon2id with 2 GiB memory, 1 pass, and 4 lanes.
- **Second recommended option:** Argon2id with 64 MiB memory, 3 passes, and 4 lanes.

These recommendations serve different resource environments. They should not be treated as interchangeable performance settings.

A practical selection process should consider:

1. Available memory on the authentication server.
2. Expected login traffic and concurrent password verifications.
3. Acceptable authentication latency.
4. The resources an attacker would need to perform offline guessing.
5. The possibility of increasing costs as hardware improves.

The chosen configuration should be benchmarked under realistic application load. A configuration that is too expensive can create resource exhaustion and affect legitimate users.

The goal is to make password guessing expensive without making normal authentication impractical.

## How Password Verification Works

Password hashing is part of the authentication lifecycle.

At a conceptual level, the process has two stages.

### During Registration

1. A user chooses a password.
2. The application generates a unique random salt.
3. A password hashing algorithm processes the password with the salt and selected parameters.
4. The resulting password verifier, salt, algorithm identifier, and relevant parameters are stored.

The original plaintext password is not retained.

### During Login

1. A user submits their password.
2. The application retrieves the stored password verifier and its associated parameters.
3. The submitted password is processed using the stored hashing configuration.
4. The result is verified against the stored verifier.
5. Authentication succeeds only if verification is successful.

A secure password hashing library generally provides the required salt generation, parameter encoding, and verification functionality.

## Password Hashing and Database Breaches

Password hashing reduces the impact of a database breach, but it does not make a stolen database harmless.

An attacker may still attempt offline password guessing using the stolen password verifiers.

The effectiveness of password storage therefore depends on several factors:

- The strength and uniqueness of user passwords.
- The hashing algorithm.
- The selected cost parameters.
- The use of unique salts.
- The protection of any additional secrets, such as a pepper.

Weak or commonly reused passwords may still be recovered through guessing attacks.

Password hashing should be combined with other authentication protections, including multi-factor authentication, rate limiting, secure account recovery, and monitoring for suspicious activity.

## Common Password Storage Mistakes

Several mistakes can undermine an otherwise secure authentication system.

- **Storing plaintext passwords:** A database breach immediately exposes users' credentials.
- **Using SHA-256 directly:** Fast general-purpose hashing makes offline guessing easier.
- **Reusing salts:** Identical passwords may produce identical hashes, and precomputation becomes more useful.
- **Using outdated algorithms:** Older password hashing configurations may no longer provide sufficient protection.
- **Choosing extremely low cost parameters:** Attackers can perform more guesses within the same amount of time.
- **Ignoring resource limits:** Excessively expensive configurations can make authentication vulnerable to resource exhaustion.
- **Treating a pepper as a salt:** A pepper must remain secret and be stored separately.
- **Keeping old hashes indefinitely:** Password verifiers should be upgraded when users authenticate if stronger parameters become available.

## Upgrading Password Hashes Over Time

Security requirements change as computing hardware improves and password-cracking techniques evolve.

A password hashing configuration that was acceptable several years ago may no longer provide sufficient protection.

Applications should periodically review their hashing parameters.

When a user successfully authenticates using an older configuration, the application can determine whether the stored verifier needs an upgrade.

If an upgrade is necessary, the submitted password can be processed using the newer configuration and the stored verifier can be replaced.

This approach allows applications to strengthen password storage gradually without requiring every user to reset their password immediately.

## Password Hashing Is Only One Layer of Security

Secure password storage is an important part of authentication, but it cannot independently protect an entire account.

A complete authentication system should also consider:

- Strong password policies that encourage unique passwords.
- Multi-factor authentication.
- Secure login and password-reset processes.
- Rate limiting and protection against automated guessing.
- Secure transmission of credentials over HTTPS.
- Appropriate access controls for password databases.
- Monitoring and response procedures for credential breaches.

Password hashing protects stored credentials. The broader authentication system protects the account and the user.
